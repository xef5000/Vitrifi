# Generated features from Java and Spring

Vitrifi 0.3 derives feature views from real Java source. You annotate feature identity, resource names, and intended policies. The tool obtains method signatures and supported call relationships from `javac`, resolves a bounded set of Spring injection patterns, and recognizes supported SQL effects. It generates the `.vitrifi` review file beside the feature's Java implementation.

This is the first implementation of the generated workflow. The earlier [authored language](language.md) and its five syntax adapters remain available. Generation and instrumented verification currently support the Java/Spring integration described here; they are not yet implemented for the other host languages.

## What you write

The [checkout service](../examples/spring-checkout/src/main/java/dev/vitrifi/example/checkout/DiscountService.java) contains ordinary application code and small annotations:

```java
@Service
@Feature(value = "Checkout.Discounts", purpose = "Apply coupons without writes on rejection")
public class DiscountService {
    private final CartRepository carts;

    public DiscountService(CartRepository carts) {
        this.carts = carts;
    }

    @NoEffectOnError(action = "write", resource = "Carts")
    public Receipt applyCoupon(String actorId, String cartId, String code) {
        // Normal validation and persistence implementation.
    }

    @Forbid(action = "write", resource = "Carts")
    public Cart preview(String cartId) {
        return carts.load(cartId);
    }
}
```

This is an excerpt; the complete source includes the method body. There is no handwritten copy of the signature, binding, or call list in a feature file.

| Annotation | Meaning |
| --- | --- |
| `@Feature(value, purpose)` | Names a feature on a class or package. Public source methods provide its entry operations. Purpose remains authored prose. |
| `@ResourceTable(value, table)` | Gives a database table its architectural resource name. Place it on the repository class, for example `@ResourceTable(value = "Carts", table = "carts")`. |
| `@Forbid(action, resource)` | Prohibits that resource effect. Static analysis checks reachable recognized effects; the runtime guard blocks a matching JDBC operation before executing it. |
| `@NoEffectOnError(action, resource)` | Requires no matching JDBC execution attempt if the annotated operation exits exceptionally. This requires an exercised error path and runtime evidence. |

Policy annotations are repeatable. The language vocabulary includes `read`, `write`, `network`, and `emit`, but this runtime integration instruments JDBC `read` and `write`. Other policy actions do not get a successful runtime verification claim.

A resource annotation supplies the table's meaning. It does not declare that a repository method is harmless or that a method called `save` must write. The SQL adapter examines the actual supported `JdbcTemplate` call and its SQL; the runtime wrapper intercepts actual JDBC execution attempts.

## Build and generate

Requirements: a full JDK 21 or newer, Maven, and the Rust toolchain. Point `JAVA_HOME` to the JDK. From this repository's root:

```sh
cargo build
mvn install
mvn -f examples/spring-checkout/pom.xml generate-resources

./target/debug/vitrifi generate --root examples/spring-checkout
./target/debug/vitrifi check --java --root examples/spring-checkout
```

The Maven reactor builds the analyzer/runtime JAR, runs Java tests, installs the local integration artifact, and writes the example's dependency classpath to `target/vitrifi-classpath.txt`. The following `generate-resources` command prepares the classpath used by a standalone `mvn test` in the example directory, resolving the installed artifact instead of its reactor build path. Prepare that classpath before Vitrifi fingerprints it: dependency or classpath changes during verification invalidate the evidence.

`generate` invokes the analyzer with annotation processing disabled. It does not load Spring, instantiate application beans, run tests, or execute application static initializers.

The generated file is [Checkout.Discounts.vitrifi](../examples/spring-checkout/src/main/java/dev/vitrifi/example/checkout/Checkout.Discounts.vitrifi). Read it in a PR to follow the service through the resolved repository implementation and SQL effects. Native signatures and source identities are retained, alongside modeled calls, transitive effects, policies, and unresolved relationships.

`generate` writes snapshots. `generate --check` and `check --java` compare them against newly analyzed source without writing. They fail for stale or obsolete output, analysis errors, forbidden effects, or unresolved reachable calls. Replacing authored files is refused. Obsolete generated files are reported for explicit removal.

Generated files begin with `// @generated by vitrifi source analysis`. Commands that encounter this marker select the Java analysis workflow rather than treating the generated declarations as independent claims. Use the application's module directory as `--root`; a repository containing several independently built Java applications needs a classpath and analysis invocation for each application.

Java commands analyze the entire `--source-root`. A positional `.vitrifi` path can select the Java workflow, but it does not narrow analysis or verification to that feature.

The default source directory is `src/main/java`. To use another application or installation:

```sh
vitrifi generate --root /path/to/application \
  --java-analyzer /path/to/vitrifi-java-0.3.0.jar \
  --classpath-file target/vitrifi-classpath.txt \
  --source-root src/main/java
```

`--source-root` and `--classpath-file` are relative to `--root`. The classpath file contains the platform-separated Java classpath; relative entries are relative to the application root. You can set `VITRIFI_JAVA_ANALYZER` instead of passing the JAR each time, and `VITRIFI_JAVA` to select a Java executable. In this repository, the CLI defaults to the built JAR under `integrations/java/target/` when invoked from the repository root.

## Verify behavior against the real implementation

The example uses an actual Spring context, constructor injection, `JdbcTemplate`, and an H2 database. It enables runtime instrumentation with `@Import(VitrifiSpringConfiguration.class)`.

Its tests start one `EvidenceSession` per verification command, run named scenarios, and call `verify()` after all scenarios. A scenario can catch `CouponRejected` using an ordinary test assertion. Vitrifi still remembers whether the rejected invocation attempted a write. Reusing the same trace destination for another session marks the evidence incomplete instead of replacing an earlier failure with a later success.

```sh
./target/debug/vitrifi verify --java --root examples/spring-checkout -- mvn test
./target/debug/vitrifi evidence --java --root examples/spring-checkout
```

Everything after `--` is the explicit command to execute, from the application root. The default limit is 120 seconds; `--timeout` accepts 1–3600 seconds. Static analysis must succeed before the command runs.

Verification requires a fresh, completed runtime session for this invocation of the CLI. A zero command exit code alone is insufficient. Missing reports, missing feature invocations, unsupported instrumentation, unmatched policies, or an untested error path prevent a passing result. Source, test, analyzer, or classpath changes invalidate the relevant recorded evidence. Reports are local generated data under `.vitrifi/`, not committed feature source.

`@Forbid` and `@NoEffectOnError` behave differently. A forbidden operation is blocked before reaching the driver. A write followed by a rejection is recorded as a violation after the feature throws; this check does not undo the write. The promise being tested is **no JDBC write execution attempt**, including an attempt that fails or is later rolled back. It is not a claim about durable state after transaction completion.

## Review implementation changes

```sh
./target/debug/vitrifi review --java --root examples/spring-checkout --base origin/main
./target/debug/vitrifi inspect --java --root examples/spring-checkout --json
```

Review analyzes both source revisions. A host-only method, dependency, effect, or policy change can therefore appear even when the committed `.vitrifi` snapshot was not regenerated. It compares semantic facts and ignores source-location shifts. Policy changes are reported separately from implementation facts.

Both revisions use the current analyzer and dependency classpath. Review does not run an old build or execute historical repository code. An incompatible historical source revision produces diagnostics rather than a clean comparison; changes to dependencies need normal build review too.

Regeneration does not loosen policy. Adding a write to `preview()` produces a real derived write and a violation of its unchanged `@Forbid`. Updating the snapshot cannot make that violation pass.

## Scope of the current guarantee

The Java adapter uses actual compiler symbols, including overload identities and parameter types. It follows supported source calls and a bounded set of Spring constructor-injection relationships when the target is unambiguous. It records call-site locations and reasons for resolved, modeled, and unknown relationships. A narrow set of standard value operations has explicit summaries; unsupported external behavior remains unknown.

Supported database effects come from simple single-table prepared `SELECT`, `INSERT`, `UPDATE`, and `DELETE` statements with registered resource mappings. Static and runtime analysis share the supported SQL classifier. Dynamic SQL, complex queries, custom SQL functions, and unsupported targets do not receive a harmless-effect classification.

The runtime scope is synchronous calls entering Spring feature proxies and JDBC operations through instrumented Spring `DataSource` beans. It detects several unsupported proxy and instrumentation cases, but this is not a sandbox for arbitrary Java. Directly created uninstrumented clients, asynchronous work, reflection, custom proxies, unmodeled libraries, database triggers, stored procedures, and durable transaction outcomes require additional adapters or analysis. Unsupported analyzed paths and instrumentation gaps are reported as incomplete, while external behavior outside the supported observation boundary remains outside the guarantee.

A passing static result means the supported architectural facts and static policies check out. `NoEffectOnError` remains marked `runtime_required` until the instrumented scenarios exercise it. Passing runtime evidence describes those captured scenarios; it does not prove every business rule or unexecuted path.
